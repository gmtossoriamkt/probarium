# Статья для probarium.ru: от строки контент-плана до PR

Работаешь в репозитории probarium.ru (GitHub `gmtossoriamkt/probarium`). Цель — достоверная, SEO-оптимизированная статья, опубликованная через PR. В main напрямую не пушишь никогда: публикация = merge PR владельцем (или тобой по его прямой команде). Пуш в рабочую ветку `blog/*` разрешён без подтверждения. Workflow деплоя (`.github/workflows/deploy-dist.yml`) не меняешь. Сначала прочитай `CLAUDE.md` — его правила обязательны и здесь.

## 0. Выбор задачи

1. Переведи в `done` все строки `content-plan.csv` со статусом `pr`, чьи PR уже смержены в main (`gh api "repos/gmtossoriamkt/probarium/pulls?state=closed&per_page=50"` — поле `merged_at`, или по наличию `blog/<slug>/index.html` в `origin/main`). Эти правки включи в PR текущей статьи.
2. Если в запросе указан номер статьи — бери его, иначе первую строку со статусом `todo` (по порядку номеров `num`). Автоматически не делаешь (пропускаешь, оставляешь `todo` и называешь в итоге): `format` = «Инструмент» (калькуляторы, тесты, лид-магниты — это не статьи); заголовки «Кейс: …» — нужны реальные данные проектов, придумывать нельзя; страницы-хабы вместо статьи (FAQ-банк, лента новостей). Остальные «Кейс» и «FAQ-хаб» (разборы проблемных ситуаций) — обычные статьи. Колонки контент-плана: `title` — рабочий H1, `angle` — тезис, `persona` — поисковый интент, `format` — Pillar / Cluster / Кейс / FAQ-хаб / Инструмент, `funnel` — TOFU/MOFU/BOFU; пустые `main_keyword`…`volume` подбираешь сам и указываешь в PR.
3. Создай от свежего main (`git fetch origin main && git checkout -b blog/<номер>-<короткий-слаг> origin/main`) ветку `blog/<номер>-<короткий-слаг>`. Если ветка создана автоматически с другим именем — работай в ней, но укажи номер статьи в заголовке PR. Поставь статус `in-progress`.
4. Если есть `factcheck/<номер>.md` — это фактчекинг редактора: учти все замечания, рекомендованный заголовок и структуру. Фактчекинг — тоже вторичный источник, его утверждения проверяются (в нём бывают ошибки в реквизитах и датах: например, «Решение Коллегии» вместо «Решение Совета», неверная дата документа FDA).
5. Если фактчекинга нет — сделай его сам: какие понятия смешаны в теме (клинические данные ≠ клиническое испытание ≠ экспертиза; разрешение ≠ уведомление; национальные правила ≠ ЕАЭС), какие тезисы рискованны, какой заголовок не обещает лишнего.
6. Проверь дубли: `grep -ril "<ключ>" blog/*/index.html` и title/H1 в `blog/index.html`. Если статья по теме уже есть — не публикуй вторую: открой PR как draft с предложением (дополнить старую или развести интенты) и пометкой «нужно решение человека».

## 2. Текст

Формат (как в существующих статьях probarium):
- H1 — заголовок. Байлайн («Автор: … , генеральный директор Probarium») уже есть в шаблоне страницы — в тексте его не пишешь.
- Вводный абзац (`lead`) и блок **«Суть в четырёх предложениях»** (H2 с таким названием или «Короткий ответ» + абзац) — ровно четыре предложения с главным ответом на интент.
- 1–2 предложения-связки со ссылками на опорную статью кластера и близкие статьи.
- Разделы H2, таблицы там, где идёт сравнение; практический чек-лист / алгоритм; таблица «Типичные ошибки».
- FAQ из 5 вопросов под H2 «Частые вопросы» (на странице — `<details class="faq-item">`, ответ 1–3 предложения).
- CTA: финальный блок страницы (`cta` в JSON генератора: вопрос к читателю в `h2`, абзац «Probarium помогает…» в `p`, кнопка на профильную страницу услуги или `/kontakty/`). Блоки «Что делать дальше» и инлайн-плашку вставляет `blog-enhance.js` по кластеру из `scripts/blog-cta-map.js`.
- H2 «Нормативная база» — полные реквизиты, редакции, номера пунктов; международные документы — отдельной строкой с пометкой «не нормативные акты РФ».
- Экспертные пометки для рецензента (курсив, «уточнить у эксперта») на страницу не выносятся — только в описание PR.

Правила содержания:
- Каждый конкретный факт (пункт, дата, срок, метрика, требование) — только если подтверждён первоисточником. Нет подтверждения — обобщи или убери.
- Не путай: клинические данные / испытание / оценка / экспертиза; разрешение / уведомление; изделие / IVD / ПО; национальный маршрут / ЕАЭС; российские требования / международные ориентиры (FDA, MDCG, IMDRF — только как ориентиры).
- Не обещай результат («КИ не нужны», «регистрация гарантирована») — пиши условия.
- Тон эксперта-практика, без воды; русская типографика (« », —).
- Объём — как в контент-плане (обычно 6000–10000 знаков; pillar — больше).

## 3. Шаг 0 — сверка

Перед сборкой страницы пройди по тексту и для каждого факта отметь: подтверждено (источник, пункт) / исправлено / убрано / не проверено. Это отчёт для описания PR.

## 4. Сборка страницы

1. Страница собирается генератором `scripts/mk-article.js` по образцу последней опубликованной статьи (первая карточка `blog/index.html`): напиши JSON статьи (формат — в начале скрипта; держи его во временной папке, не в репозитории) и запусти `node scripts/mk-article.js статья.json` (`--dry-run` — проверка без записи). Адрес `/blog/<slug>/` — латиница, со слэшем на конце.
2. Короткий title: ≤ 60 символов вместе с суффиксом « — Probarium» (суффикс — только если база ≤ 48; иначе без суффикса). Итоговый `<title>` выставляет `blog-seo.js` (ручные формулировки — `TITLES`/`DESCRIPTIONS` в нём). Description 120–160 символов. Не дублируют ключи соседних статей (grep по title). В отчёте укажи итоговую длину title.
3. JSON-LD: `BlogPosting` (или `TechArticle` для технических разборов) + `BreadcrumbList` + `FAQPage` — генератор строит FAQPage из того же списка, что и видимый FAQ (дословно). Дата публикации — сегодня.
4. Таблицы — в адаптивной обёртке `.table-wrap` (генератор делает это сам для блоков `table`).
5. Карточка: `node scripts/add-blog-card.js --slug <slug> --title "<H1>" --desc "<description>" --date <ГГГГ-ММ-ДД>` (вставляет карточку первой, пересобирает ItemList, добавляет запись в `sitemap.xml`). Затем `node scripts/blog-enhance.js` и `node scripts/blog-seo.js` (стандартный порядок; повторный прогон обоих ничего не должен менять — проверь `git status`).
6. CTA-кластер: добавь slug в `CLUSTER_OF` в `scripts/blog-cta-map.js` (кластеры: `cost`, `docs`, `clinic`, `forms`; без записи — `general`) до запуска `blog-enhance.js`.
7. Обратные ссылки: в 2–5 тематически близких статьях — по одному предложению со ссылкой (в тексте или в блоке «Читайте также», вне маркеров `<!--enh:*-->`). Это несодержательная правка: даты не менять. Если меняешь содержание опубликованной статьи (факты, нормы, формулировки) — по постоянному правилу ставь «Обновлено: <дата>», dateModified и lastmod на сегодня, затем `node scripts/blog-seo.js`; datePublished не трогать.
8. sitemap.xml обновлён (запись новой статьи — `add-blog-card.js`, lastmod — `blog-enhance.js`).

## 5. Проверки

- `node scripts/check-site.js` — 0 ошибок и 0 предупреждений (включая сверку дат и FAQ = JSON-LD); `bash scripts/check-injections.sh` — 0 находок.
- Локально: `node scripts/serve.js` (http://localhost:8792/), страница 200, на 1280 и 375 нет горизонтальной прокрутки (Playwright, Chromium уже установлен), ссылки рабочие, FAQ = JSON-LD.
- Красная проверка — исправь и повтори. PR с красными проверками не открывай.

## 6. PR

1. Статус в `content-plan.csv` → `pr`, в `url` — адрес статьи (`https://probarium.ru/blog/<slug>/`).
2. Коммит, `git push -u origin <ветка>` (в main — никогда).
3. PR в main через `gh api repos/gmtossoriamkt/probarium/pulls -f title=… -f head=<ветка> -f base=main -f body=@файл` (`gh pr create` в облачной сессии не работает; для черновика — `-F draft=true`; текст описания — из файла во временной папке) по шаблону `.github/pull_request_template.md`. Заголовок: `blog: <№> <тема>`. В описании: адрес, title (с длиной)/description; отчёт шага 0; что не проверено и почему; экспертные пометки; изменённые файлы и статьи с обратными ссылками; адреса для переобхода в Яндекс.Вебмастере (новая статья, /blog/, статьи с обратными ссылками).
4. Ветки не удаляй (из сессии запрещено; удаляются автоматически после merge).
5. В конце — короткий итог со ссылкой на PR.
6. После merge (если мержишь по прямой команде владельца) деплой идёт сам: main → GitHub Actions → `timeweb-dist` → Timeweb; проверка — `node scripts/check-prod.js blog/<slug>/` (адрес без ведущего «/»).

## Если что-то пошло не так

- Тема методически некорректна, а фактчекинга нет → напиши статью с исправленным заголовком и объясни в PR.
- Первоисточник по ключевому тезису недоступен, а смягчить нельзя → PR как draft с пометкой «нужно решение человека».
- Деплой probarium иногда не подхватывается Timeweb автоматически — это не твоя задача в рамках статьи; не меняй workflow деплоя.
